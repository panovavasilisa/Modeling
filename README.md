# PharmDelivery backend

Учебная имитационная модель службы доставки лекарств. C++17, Qt, шаг — один день.
Все исходные объявления в `back/*.h` сохранены. Объявления управления из `main.cpp`
перенесены в новый `back/simulation.h` с прежними именами и сигнатурами.

Курьеры представлены исходным числом `M`, индексами в списке доставок и массивом
нагрузки по дням. Отдельного класса курьера нет.

## Сборка и запуск

Нужны компилятор C++17, make и Qt Core/Gui/Widgets с qmake. Qt Widgets подключён
для существующего `QApplication`; консольный backend по умолчанию использует
платформу `offscreen` и не требует доступа к графической сессии.

```bash
cd /home/toster/prac-backend
mkdir -p build-backend
cd build-backend
qmake6 ../PharmDelivery.pro
make -j2
./PharmDelivery --days 15 --couriers 5 --medicines 25 --markup 25 --seed 42
```

Для Qt 5 вместо `qmake6` используйте `qmake`. Путь `back` добавлен в настройки
сборки для исходного `#include <store.h>`, сам заголовок не менялся.

Пример с настраиваемыми скидками и отчётом:

```bash
./PharmDelivery --days 25 --couriers 7 --medicines 35 \
  --markup 20 --card-discount 4 --bulk-discount 2 --regular-discount 3 \
  --max-discount 9 --seed 71 --quiet --report experiment.json
```

`--help` показывает все параметры. `--orders` печатает данные каждой доставки,
`--quiet` оставляет итоговый отчёт. Без этих флагов выводятся каталог, события дня,
остатки и нагрузка курьеров. Seed по умолчанию — 5489; поменяйте его для другого
случайного эксперимента.

Проверяются диапазоны `10 <= N <= 25`, `3 <= M <= 9`, `15 <= K <= 35`, конечность
чисел и допустимые скидки. Наценка задаётся в процентах, например `25`, а не `0.25`.

## Начальный склад

По умолчанию каждому лекарству выделяется 80 упаковок, разделённых между двумя
партиями с разными сроками годности. `--initial-count C` меняет количество.
Каталог и закупочные цены генерируются воспроизводимо по seed.

Можно полностью заменить начальные партии CSV-файлом:

```bash
./PharmDelivery --days 10 --couriers 5 --medicines 15 \
  --stock ../examples/initial-stock.csv --seed 42 --report experiment.json
```

Формат строки:

```text
medicine_id,count,expiration_day,unit_price
0,20,2,100
0,60,90,100
1,80,45,150
```

Индексы лекарств — от `0` до `K-1`; повторный индекс задаёт ещё одну партию.
Срок — день эксперимента, по окончании которого партия просрочена.
Цена — закупочная цена одной упаковки этой начальной партии. Последний столбец
можно опустить: тогда используется оптовая цена из каталога. Допускаются пустые
строки и комментарии после `#`. Файл заменяет весь набор партий; лекарства,
не указанные в нём, первоначально отсутствуют.

## Ежедневный цикл

Инициализация создаёт каталог, партии и постоянных покупателей, применяет
начальную уценку и учитывает закупочную стоимость начального запаса.
Затем каждый день выполняются исходные функции в таком порядке:

1. `manage_warehouse(day)` списывает просроченные партии, уценивает партии с
   остатком срока не более 30 дней, учитывает потери и принимает готовые поставки.
2. `generate_daily_events(day)` формирует плановые покупки по `next_purchase_day`
   и `periodicity`, а затем статистический поток обычных заказов.
3. `process_daily_order(day)` доставляет покупки, выделенные вчера, распределяет
   их по `M` курьерам и проверяет нагрузку по фактическому списку доставок. Затем
   выделяет доступные лекарства под доставку завтра и формирует заявки пополнения.
4. `cleanup_random_customers()` удаляет разовых покупателей, больше не нужных
   очереди, исправляет индексы оставшихся клиентов и сохраняет результаты дня.

Товар снимается со склада при выделении заказа; доход признаётся при доставке
на следующий день. Партии расходуются по ближайшему сроку годности. Партия,
просроченная к дню доставки, в неё не включается. При нехватке выдаётся доступное
количество; пустая покупка не считается доставкой. Запрошенные `Order::items`
сохраняются, фактические количества записываются отдельно в результатах.
`Order::process_order` возвращает `true` при выдаче хотя бы одной упаковки.

Период содержит ровно N дней: в первый день нет вымышленных вчерашних заказов,
а покупки, выделенные в последний день, остаются ожидающими доставки. Их стоимость
и количество отражаются отдельно. Заказы постоянного клиента создаются в день,
заданный расписанием; доставка происходит следующим днём.

## Курьеры и границы нагрузки

Покупки распределяются равномерно между индексами `0..M-1`, после чего цикл по
реальным доставленным заказам повторно считает нагрузку каждого курьера.
Если число доставок находится между `7*M` и `15*M`, каждому достаётся 7–15 покупок.

При числе покупок меньше `7*M` требование минимума математически невыполнимо:
отчёт показывает недогрузку. Фиктивные заказы не создаются. На завтра выделяется
не более `15*M` покупок; превышение остаётся в очереди до выделения товара.
Такие заказы могут быть доставлены позже следующего дня, что явно отмечается
в отчёте. Исходный срок следующего дня выполняется при достаточной вместимости.

## Склад, поставки и скидки

`StoreBatch::price()` возвращает стоимость оставшихся упаковок;
`take(int)` возвращает реально выданное количество. Уценка делит продажную базу
партии пополам один раз. После дня истечения срока партия удаляется, а её
закупочная стоимость учитывается как потеря. Внутренний контекст хранит признаки
уценки и закупочные цены без добавления полей в существующие классы.

Если суммарный остаток лекарства ниже `Medicine::min_stock`, внутренний
`SupplyManager` создаёт исходный `Request` для пополнения до трёх минимальных
запасов. Пока заявка ожидает исполнения, вторая заявка на это лекарство не
создаётся. Задержка поставки равномерна: 1–3 дня от дня заявки. Поступившие
упаковки реально добавляются в склад; расходы начисляются при поступлении.

Стоимость заказа рассчитывается из фактически выделенных упаковок с учётом
уценки и наценки. Далее применяется скидка по карте либо, при отсутствии карты
и сумме после наценки строго больше 1000 рублей, скидка крупной покупки.
Постоянному клиенту добавляется его дополнительная скидка. Сумма ограничивается
настраиваемым пределом, который не может превышать 9%.

Все исходные публичные числовые поля инициализируйте через `{}`, например
`Statistics stats{};` или `Customer customer{};`.

## Случайность и предположения модели

Используется один генератор `mt19937`, задаваемый seed. В течение дня есть 180
независимых возможностей поступления заказа с вероятностью
`0.75 * exp(-markup_percent / 60)` каждая. Получается биномиальный поток с
уменьшающейся при росте наценки интенсивностью. Поток не зависит от M, чтобы
эксперименты с числом курьеров меняли вместимость, а не создавали новый спрос.

В обычном заказе случайно выбираются 1–4 различных лекарства и 1–4 упаковки
каждого; уценённое имеющееся лекарство имеет втрое больший вес выбора.
Расписание постоянных покупателей хранится отдельно и не заменяет обычный поток.
Размер пополнения и указанные распределения — явные предположения для деталей,
не определённых ТЗ.

## Статистика и результаты

`Statistics::update` накапливает доход доставок, расходы на закупку и потери.
Начальные запасы считаются приобретёнными перед началом эксперимента.
Итоговая прибыль выражается двумя равными способами:

```text
доход - закупки + стоимость доступного запаса + стоимость выделенного товара
доход - себестоимость доставленного товара - потери от списания
```

Стоимость непроданных и ожидающих доставки упаковок учитывается как запас.
Потери повторно не вычитаются из первого выражения. Денежный поток
`доход - закупки` отличается от прибыли на стоимость оставшихся запасов.
Модель проверяет финансовый баланс после каждого дня.

JSON включает параметры, каталог, ежедневные остатки, доставленные заказы с
клиентами, запросом и фактической выдачей, нагрузку курьеров, партии склада,
ожидающие поставки и итоговые суммы.

Для подключения frontend используются `configure_simulation(parameters)`,
`init_simulation()`, четыре ежедневные функции выше и `simulation_result()`.
Результат дня готов после `cleanup_random_customers()`; перед новым экспериментом
снова вызовите настройку и инициализацию. Исходный глобальный контракт рассчитан
на один эксперимент в процессе. Консольный интерфейс находится отдельно от
логики модели. Файлы frontend этим backend не изменяются.

## Проверки

```bash
cd /home/toster/prac-backend
bash tests/run_tests.sh
python3 tests/cli_tests.py build-backend/PharmDelivery
```

Проверка ошибок памяти и неопределённого поведения:

```bash
ASAN_OPTIONS=detect_leaks=0 SANITIZE=1 bash tests/run_tests.sh
```

`detect_leaks=0` используется в средах с ptrace, где LeakSanitizer недоступен.
AddressSanitizer и UndefinedBehaviorSanitizer при этом работают.

Проверки охватывают полную, частичную и отсутствующую выдачу, несколько партий,
сроки годности и однократную уценку, реальные поставки и защиту от повторных
заявок, все скидки, периодические покупки, зависимость спроса от наценки,
повышенный спрос на уценённое, перегрузку и недогрузку курьеров, повторные
эксперименты, сохранение количества упаковок и стоимости, JSON и ввод.
Все восемь сочетаний границ N=10/25, M=3/9, K=15/35 проверяются.
