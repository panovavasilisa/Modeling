# PharmDelivery

Итоговый проект: `/home/toster/prac`. C++17, Qt Widgets. Приложение открывает
графическое окно; backend представляет собой вызываемую из него модель C++.
Шаг моделирования — один день. HTTP-сервера и базы данных нет.

## Сборка и запуск

```bash
cd /home/toster/prac
mkdir -p build
cd build
qmake6 ../PharmDelivery.pro -after \
  'SOURCES = $$unique(SOURCES)' \
  'HEADERS = $$unique(HEADERS)'
make -j2
./PharmDelivery
```

Команды `unique` исключают повторные записи `front/animtab.cpp` и
`front/animtab.h` из исходного `.pro` при генерации Makefile. Для Qt 5
используйте `qmake` вместо `qmake6`.

Текущий `main.cpp` создаёт `MainWindow` и запускает цикл событий Qt.
Аргументы `--days`, `--report`, `--quiet` и остальные параметры старого
консольного запуска здесь не обрабатываются. `offscreen` автоматически
не устанавливается.

## Параметры backend и текущего окна

Поля `SimulationParameters` объявлены в `back/simulation.h`, ограничения
проверяются в `SimulationParameters::validate()` в `internal/simulation_engine.cpp`.
`MainWindow::buildParameters()` считывает форму и передаёт структуру через
`configure_simulation()`, затем вызывается `init_simulation()`.

| Параметр | Backend: значение по умолчанию | Текущая форма |
| --- | --- | --- |
| Дни N | 15; диапазон 10–25 | 15; 10–25 |
| Курьеры M | 5; 3–9 | 5; 3–9 |
| Виды лекарств K | 25; 15–35 | 25; 15–35 |
| Наценка | 25%; 0–10000% | 25%; 0–100% |
| Скидки: карта / крупная покупка / постоянный | 5 / 3 / 5%; каждая 0–100% | 5 / 3 / 5%; каждая 0–9% |
| Общий предел скидки | 9%; 0–9% | 9%; 0–9% |
| Новых заказов в день | 180; 0–100000 | 20; 1–200 |
| Начальный капитал | 1000000 ₽; конечный и неотрицательный | 1000000 ₽; 0–1000000000 |
| Порог пополнения | 20; 0–1000000 | 20; 1–100 |
| Дней до уценки | 30; 0–1000000 | 30; 1–90 |
| Вероятность выбора уценённой категории | 0.75; 0–1 | 75%; делится на 100 |
| Упаковок каждого лекарства | 80; 0–1000000 | Отдельного поля нет |
| Постоянных покупателей | 10; 0–100000 | В коде формы задано 10 |
| Seed | 5489; uint32 | В коде формы задано 5489 |
| CSV начального склада | Пустой путь | Поля выбора файла нет |

Пример фактической передачи значений формы:

```cpp
SimulationParameters p;
p.orders_per_day = ui->ordersPerDaySpin->value();
p.initial_capital = ui->capitalSpin->value();
p.restock_threshold = ui->thresholdSpin->value();
p.markdown_days = ui->expiryDaysSpin->value();
p.discounted_probability = ui->discountedProbSpin->value() / 100.0;
configure_simulation(p);
init_simulation();
```

В этом сокращённом примере остальные поля имеют значения структуры;
полный перенос остальных полей реализован в `MainWindow::buildParameters()`.

## Один день модели

1. `manage_warehouse(day)` — приём поставок, списание просрочки, однократная уценка.
2. `generate_daily_events(day)` — плановые покупки и случайные заказы в общей очереди.
3. `process_daily_order(day)` — доставка подготовленного вчера, проверка нагрузки,
   подготовка покупок на завтра и заявки поставщику.
4. `cleanup_random_customers()` — очистка клиентов, обновление индексов и сохранение дня.

Начинать следует с настройки и инициализации, затем выполнять дни 1…N по порядку.
В окне перед первым шагом используйте генерацию или старт.

Товар снимается со склада при подготовке покупки; доход учитывается при доставке.
Партии выбираются по ближайшему сроку годности, проверяется годность на завтра.
При нехватке выдаётся доступное количество. Недостача не превращается в новый заказ.
В первый день доставок нет; подготовленное в последний день остаётся ожидающим.

Курьеры — число M и индексы массива нагрузки, отдельного класса курьера нет.
Назначение: `(i + day - 1) % M`, вместимость — `15*M` покупок.
При количестве доставок от `7*M` до `15*M` нагрузка каждого составляет 7–15.
Недогрузка отмечается флагом, лишние заказы ждут в очереди; возможны опоздания.

## Спрос, склад и финансы

Вероятность обычного заказа в каждом свободном месте дневного лимита:
`p = exp(-markup_percent / 60.0)`. Плановые покупки входят в общий лимит.
Обычный заказ содержит 1–4 разных лекарства по 1–4 упаковки каждого.
Уценённая категория выбирается с вероятностью `discounted_probability`,
если доступны обе категории; внутри категории выбор равномерный.

Партия годна в `expiration_day`, списывается при `expiration_day < current_day`.
При остатке срока не более `markdown_days` продажная база уменьшается вдвое
один раз. Закупочная цена хранится отдельно и не меняется из-за уценки.
Пополнение ниже порога: `3*min_stock - текущий остаток`, задержка — 1–3 дня;
ожидающая заявка блокирует повторную на то же лекарство.

Скидка: карта **либо** покупка строго дороже 1000 ₽ без карты; затем добавляется
скидка постоянного покупателя и применяется общий предел не более 9%.

```text
прибыль = доход - себестоимость доставленного - потери от списания
        = доход - все закупки + доступный запас + подготовленный запас
деньги  = начальный капитал + доход - все закупки
```

В формулах запас оценивается по закупочным ценам. Бюджет не ограничивает закупки;
денежный баланс может быть отрицательным. Деньги хранятся как double.

## CSV и JSON

Backend поддерживает `initial_stock_file`: CSV полностью заменяет начальные партии.
Строка: `medicine_id,count,expiration_day[,unit_price]`; ID от 0 до K−1.
Если цена пропущена, используется оптовая цена каталога. Пример — `examples/initial-stock.csv`.

Сериализатор `model_detail::write_json_report(path)` находится в
`internal/simulation_cli.cpp`. В текущую GUI-сборку модуль не включён и из окна
не вызывается. Для использования экспорта отдельный потребитель должен явно
подключить этот модуль и вызвать функцию после инициализации или завершения дня.
JSON содержит `parameters`, `totals`, `catalog`, `days`, `completed_orders`,
`inventory`, `pending_supplies`. Полное описание — в документации.
