# PharmDelivery backend

Учебная модель службы доставки лекарств, C++17 и Qt. Существующие объявления
в `back/*.h` сохранены без изменений.

## Проверенный этап реализации

Реализованы партии и склад, частичная выдача заказа, расход партий по ближайшему
сроку годности, однократная уценка за 30 дней, списание, наценка и настраиваемые
скидки с верхней границей 9%. Доход заказа соответствует фактической выдаче.
Генератор создаёт каталог, начальные партии, постоянных и разовых клиентов,
позиции заказов и сроки поставок. Используется один генератор `mt19937`.

Внутренний `SupplyManager` использует исходный класс `Request`: пополняет остаток
до трёх минимальных запасов, не создаёт повторную заявку до поступления и принимает
поставки через равномерно распределённые 1–3 дня. Расходы начисляются при поступлении.

Вероятность появления заказа в одной возможности поступления:
`0.75 * exp(-markup_percent / 60)`. Число возможностей в ежедневном цикле ещё не
задано. В заказе 1–4 различных позиции по 1–4 упаковки; вес уценённого лекарства
при выборе позиций втрое выше обычного. Эти распределения — предположения модели,
поскольку ТЗ не задаёт конкретный закон поступления заказов.

Для реализации неизменяемого `Warehouse::write_off(int)` внутренний контекст
хранит закупочную стоимость и признак уценки каждой партии. Повторная уценка
не применяется. Метод `collect_write_off` внутреннего контекста отдаёт накопленные
события списаний ровно один раз для вызова исходного `Statistics::update`.
Уценка меняет продажную базу, сохраняя закупочную стоимость для финансового баланса.

`Order::process_order` возвращает `true`, если выдана хотя бы одна упаковка,
включая частичное выполнение. `items` сохраняет запрошенные позиции;
фактическая выдача доступна во внутреннем контексте. Неверные индексы и отрицательные
количества отклоняются до изменения остатков. Объекты с исходными публичными
числовыми полями следует инициализировать через `{}`, например `Statistics stats{};`.

**Ежедневный цикл и распределение курьерам пока не подключены.** Исходный `main`
по-прежнему запускает цикл событий `QApplication`; запуск приложения ещё не
является запуском эксперимента. Продолжение требует согласования отсутствующего
в исходной архитектуре класса курьера. Генератор, склад, заказы и поставки
проверяются отдельно от приложения.

## Сборка

Нужны компилятор C++17, make и Qt Core/Gui/Widgets с qmake.
Qt Widgets подключён для уже существующего `QApplication`.
Путь `back` добавлен в настройки сборки для исходного `#include <store.h>`.

```bash
cd /home/toster/prac-backend
mkdir -p build-backend
cd build-backend
qmake ../PharmDelivery.pro
make -j2
```

Сборка этого этапа проверена с Qt 5.15.19 и GCC 16.2.1.

## Проверки

```bash
cd /home/toster/prac-backend
bash tests/run_tests.sh
```

Проверка ошибок памяти и неопределённого поведения:

```bash
ASAN_OPTIONS=detect_leaks=0 SANITIZE=1 bash tests/run_tests.sh
```

`detect_leaks=0` требуется в средах с ptrace, где LeakSanitizer не работает.
Обычная команда не отключает никаких проверок функциональности.

## Финансовый баланс

В текущих проверках закупки начального запаса и поставок учитываются как расходы.
Прибыль от реализованных товаров проверяется двумя равными выражениями:

```text
доход - закупки + закупочная стоимость оставшегося запаса
доход - себестоимость проданных упаковок - потери от списания
```

Потери выводятся отдельно и повторно из первого выражения не вычитаются.
При подключении доставки на следующий день потребуется отдельно учитывать
закупочную стоимость уже выделенных, но ещё не доставленных упаковок.
